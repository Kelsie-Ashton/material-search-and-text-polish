# Design

## Context

当前仓库为空（仅有 `openspec/` 规划目录），这是一次全新搭建，没有需要兼容的既有代码或数据。

约束条件（来自 proposal 与用户确认）：

- 交付形态为**本机运行的 Web 应用**（本地服务 + 浏览器访问），不做桌面客户端打包——目的是控制工期。
- 素材来源**仅限本地磁盘**，不做任何网络素材抓取。
- 文字提取（语音转写、OCR）走**本地开源引擎**，润色走**云端大模型 API**。
- API Key **由用户在设置界面自行填写**，源码与仓库中不得出现任何密钥。
- 最终需提交到 GitHub（公开仓库），并附带中文 `README.md` 与 `.gitignore`。
- 首要目标平台为 Windows 11。
- 支持对象由**文件类型**界定：视频、音频、图片、文本（含字幕）。典型使用场景包括动漫、漫画、剧集与游戏素材的二次创作——但这些是**场景举例，不是代码里的分类维度**（见决策 11）。

关键设计压力点：转写与 OCR 是长耗时、吃资源的操作，而 Web 应用的前端在浏览器里、无法直接读本机文件。因此架构上必须把「文件访问」与「长任务执行」收拢到本地后端服务中，前端只负责交互与展示。

## Goals / Non-Goals

**Goals:**

- 单用户在**本机**运行、浏览器访问；后端可自由读写用户授权的本地目录。
- 关键词检索、文字提取、润色三条链路清晰解耦，任一条不可用时其余功能仍能工作。
- 依赖安装与首次启动尽可能简单（不要求用户预装 Python 或额外运行时）。
- 凭证与素材数据在磁盘上的落点明确、可控、默认不进版本库。

**Non-Goals:**

- 不做用户账号、登录与多租户隔离——本机单用户场景。
- 不做局域网/公网访问，服务仅绑定 `127.0.0.1`。
- 不引入 Redis、消息队列或独立数据库服务；不引入 GPU 专属运行时。
- 不做素材的云端同步、备份与跨设备共享。
- 不做向量检索与语义排序（先做基于文本匹配的检索，效果不足时再评估）。
- **不做中文以外语言的语音转写与 OCR**。当前 ASR 只配中文模型、OCR 只用 `chi_sim` 语言包；日文、英文等需另选模型并重新验证准确率，本变更不实现（见决策 12 末段与「交付批次与未来规划」）。注意此限制只针对「从语音和画面里认出文字」，**不针对字幕文件的直接解析**。
- 不做漫画压缩包（`.cbz` / `.cbr`）的解包与逐页识别——漫画素材本期以散图形式支持。
- 不把「题材」（动漫/漫画/剧/游戏）建成代码里的分类维度或筛选器（见决策 11）。

## Decisions

### 决策 1：本地 Web 应用 = Node.js 后端 + React 前端

后端负责文件系统访问、索引、任务执行与外部 API 调用；前端是纯浏览器 UI，通过 REST 与后端通信。

- **备选：Electron 桌面应用**——UI 与 Node 同进程，文件访问天然可用；但引入打包、签名、自动更新等额外工作量，与「按时完成」的目标冲突，弃用。
- **备选：纯 CLI 工具**——最省事，但无法承载用户明确要求的「设置界面」，弃用。

### 决策 2：纯 Node.js 技术栈，不引入 Python 侧车

OCR 采用 `tesseract.js`（含 `chi_sim` 中文语言包），语音转写采用 `@huggingface/transformers`（Transformers.js），二者均为纯 WASM / npm 包，随 `npm install` 一并就位，不需要任何原生编译工具链。

- **备选：`whisper.cpp` 的 Node 绑定**——原方案。调研后弃用：`nodejs-whisper` 需要用户自备 MSYS2/MinGW-w64 工具链，`smart-whisper` 的 Windows 预编译产物未能确认可用。在 Windows 上安装失败率高，与「按时完成」直接冲突。Transformers.js 走 WASM，代价是首次需下载模型，但换来「装即用」，值得。

**实施期修订（2026-09-27，已实测）**，三处与初稿不符，均已改：

1. **模型不是原定的 `onnx-community/whisper-small-chinese-2-ONNX`，改用 `Xenova/whisper-small`。** 原定模型在 Transformers.js 4.3.0 上**直接跑不通**：它的 ONNX 图要求一个 `cache_position` 输入而库不提供，报 `Missing the following inputs: cache_position`。已排除"仓库个体问题"之外的干扰项——同一段路径下 `Xenova/whisper-tiny` 与 `Xenova/whisper-small` 均正常。模型名做成可配置（`ASR_MODEL`）。
2. **体积估算错了。** 初稿写「`q8` 约 54 MB」，实测 whisper-small 的 q8 需要 `encoder_model_quantized`(88 MB) + `decoder_model_merged_quantized`(150 MB) = **238 MB**。注意只有这两份参与生成，仓库里其余十几个 `.onnx` 变体（`decoder_model_*`、`decoder_with_past_model_*`、`fp16`、`bnb4` 等）不会被下载。
3. **转写输出是繁体，必须后处理转简体。** 实测普通话语音转写得到「今天我們來探店這家火鍋店」。试过用 `initial_prompt` 偏置（`'以下是普通话的句子。'` 等），**三种提示下输出逐字相同**，这条路不通。改用 `opencc-js` 做字符级转换。**刻意不用它的 `twp` 配置**：那会做词汇映射（把「請開啟軟體」改写成「请打开软件」），而转写场景下说话人说的就是"开启"，不该替他改词。

   质量实测（一段由 Windows 中文 TTS 合成的 9.7 秒普通话）：`whisper-small` 仅错一字（「毛肚」→「毛賭」）；`whisper-tiny` 错四处（探店→看電、毛肚→毛土、鸭肠→亞長），且把「人均消费八十元」写成「80元」。**故取 small**，转写速度约 2.9x 实时。
- **备选：PaddleOCR + faster-whisper 的 Python 侧车**——中文识别质量更好，但要求用户自行准备 Python 环境与 `paddlepaddle`，在 Windows 上安装失败率高，会显著拉长首次启动链路并增加支持成本。作为**已知质量风险**保留为后续可选增强（见 Open Questions），而非 MVP 方案。
- 该决策的代价是中文 OCR 精度有上限，缓解手段：OCR 主要用于视频字幕与画面文字（字体规整、对比度高），这类场景 tesseract 表现可接受；同时允许用户手工修正提取文本。实测 tesseract.js 对中文准确率约 70–85%，且**必须预处理**（灰度化 → 二值化 → 放大 2–3 倍）才能进这个区间，直接把原图喂进去会更差——这是必要步骤，不是可选优化。

### 决策 3：SQLite 单文件库作为索引与元数据存储

使用 `better-sqlite3` 存放素材元数据、标签、提取文本与润色结果；全文检索使用 SQLite FTS5。

- **备选：JSON 文件**——实现简单但无检索能力，素材量上千后不可用，弃用。
- **备选：引入独立检索引擎**——运维成本与工期不匹配，弃用。
- **中文分词方案（已由 spike 实测确定）**：FTS5 默认 `unicode61` 分词器对中文按整段切分，效果差。采用 **trigram 分词器 + 短词 LIKE 兜底**，并对命中片段做应用层字符级重算以生成高亮上下文。

  以下是实测结论，不是推断。在 20 万段 / 585 万字的语料上：

  - **trigram 对 <3 字符的查询静默返回 0 行**。「美食」「配音」「剪辑」「探店」这类最常用的两字词一旦只走 trigram，用户**什么都搜不到且不报错**——这是本设计里唯一的需求级风险。
  - **多词查询中只要有一个短词，整个查询就废掉**（`美食 AND 视频` → 0 行，尽管两词都在文中）。因此必须**逐词分流**：≥3 字走 FTS，≤2 字走 LIKE。绝不能因为「有一个词够长」就把整个查询交给 FTS。
  - **LIKE 兜底的扫描范围是正文，不是只有文件名与标签**。这是对原规划的修正：原计划写的是「两字关键词仅搜索文件名与标签」并降级提示，但实测**正文 LIKE 全表扫 20 万段只要 24 ms**，完全负担得起。按原计划做会白白牺牲最常用的两字查询。
  - **未转义的用户输入会直接抛 SQL 错误**：实测 `美食-视频` 抛 `no such column: 视频`，`美食"视频` 抛 `unterminated string`。必须逐词双引号包裹、内部 `"` 翻倍，实测可完全中和 `-` `*` `:` `NEAR(` `AND` 等所有操作符。
  - **bm25 的 `rank` 是负数，越小越相关**。聚合时用 `MIN(rank)`——符号最容易写反，单测必须钉死。
  - **已评估并否决的方案**：`@node-rs/jieba` 分词 + unicode61，以及「分词列 + 原文列」双表。jieba 召回 98.4–99.7% 但**漏召回是结构性的**——查询词边界被更长词吞掉（剪辑「师从」/剪辑「师傅」、背景「音乐会」、火锅「店主」），改查询救不回来；双表方案召回 100% 但体积 77.9 MB。而 trigram 方案 46.1 MB，召回缺口由 LIKE 兜底补上，且 LIKE 的成本已被证明可忽略。
  - **磁盘代价**：trigram 索引净开销 ≈ 4.0x 原文，**100 MB 转写文本 → 约 540 MB 数据库文件**。这是 SQLite 中文子串检索的固有代价，README 需给出容量预期。索引写入必须搭提取任务的顺风车，绝不事后批量补（trigram 建索引比 unicode61 慢约 10 倍）。
- **FTS 同步必须用触发器，不能靠应用层写入**：external content 表**不会**在主表行删除时自动清理索引——实测删行后 `MATCH` 仍返回该 rowid，产生指向不存在素材的**幽灵条目**，用户会看到点不开的结果且极难排查。应用层方案必须记住在每个删除/更新点精确重放旧字段值，漏掉任何一处（级联删除路径、迁移脚本、手工修数据）就出错。触发器把这个不变量交给数据库，无法绕过。注意删除指令用的是 FTS 表**自身的名字**作为特殊列名（`INSERT INTO fts_segments(fts_segments, rowid, text) VALUES('delete', …)`），不是字面量 `fts`。
- **文件名与标签不进 FTS，走 LIKE**：正是由于上面第一条——两字标签一旦进 FTS 就会静默失效。且实测 10 万条文件名的 LIKE 全表扫仅 6.7 ms，3000 条标签仅 0.1 ms。短文本、小基数、期望精确匹配的场景用 LIKE；长文本、大基数、模糊子串的场景用 trigram。用错工具不但浪费磁盘，还会在用户最常用的词上无声失效。

### 决策 4：长任务采用进程内串行队列 + 状态轮询

转写与 OCR 封装为后台任务，由一个进程内队列**串行**执行（避免同时跑多个 whisper 实例把机器打满），任务状态（排队中 / 进行中 / 完成 / 失败）落库。

前端通过轮询任务状态接口刷新进度。**备选：SSE / WebSocket 推送**——实时性更好，但增加连接管理与断线重连的复杂度；本期先用轮询，接口预留为可替换（后续改为 SSE 不影响前端展示层之外的部分）。

### 决策 5：提取结果按「文件内容指纹」缓存

为每个素材记录文件大小与修改时间作为指纹；指纹未变化时直接复用既有提取结果，避免对长视频重复跑转写。

### 决策 6：润色走可配置的云端 Provider 适配层

后端定义统一的 `LLMProvider` 接口（`polish(text, options)` + `verifyCredential()`），默认实现对接 Anthropic Claude，同时支持配置 `baseUrl` 与 `model`，便于接入兼容 OpenAI 协议的服务。默认模型选择遵循「使用最新且最强的 Claude 模型」原则。

- 该适配层是**凭证缺失降级**的落点：无凭证时该层直接返回「未配置」状态，上层据此禁用入口，而非在业务代码里散落判断。

### 决策 7：凭证存放于仓库之外的本地数据目录

凭证保存在后端数据目录下的独立文件中（如 `data/credentials.json`），与源码完全分离。

- **备选：系统钥匙串（keytar 等）**——更安全，但引入原生模块编译依赖，在 Windows 上增加安装失败面，且与「按时完成」冲突；本期不做。
- **风险缓解**：数据目录整体加入 `.gitignore`；文件以仅当前用户可读写的权限创建；界面与日志统一脱敏（仅回显末四位）；README 中显式警告。
- **硬性约束落地方式**：源码中只允许出现从存储读取凭证的代码路径与环境变量占位符（如 `ANTHROPIC_API_KEY`），任何真实密钥都不得进入源码、示例配置与测试夹具；同时在仓库中提供 `.env.example`（仅含占位符）以引导用户。

### 决策 8：服务仅监听回环地址

后端绑定 `127.0.0.1`，并校验请求来源 Origin。由于该服务能够读取用户本机任意已授权目录，绝不能暴露到局域网。

### 决策 9：前端信息架构为三区

- **检索页**：关键词输入 → 结果列表（命中来源、上下文、路径）→ 类型与状态筛选。
- **素材库页**：目录管理、扫描进度、素材列表、标签编辑、提取与润色操作入口。
- **设置页**：API Key 与服务地址/模型配置、连通性测试、凭证清除。

### 决策 10：仓库工程化交付纳入本变更范围

`README.md`（中文：项目介绍、功能说明、安装与运行步骤、API Key 配置指引、常见问题）与 `.gitignore`（至少覆盖 `node_modules/`、构建产物、`data/` 凭证与索引、`.env*`、模型缓存）作为本变更的正式交付物，与功能代码同等对待。

### 决策 11：支持对象由文件类型界定，题材不进代码常量

用户会用「动漫 / 漫画 / 剧 / 游戏」这类词来描述他要找的东西，但**题材与文件类型是两件正交的事**：扩展名回答「怎么读这个文件」，题材回答「内容讲什么」。同一个 `.mp4` 既可能是番剧也可能是游戏录屏，把它归到哪一类取决于用户，不取决于文件。

因此：**题材不得出现在 `SUPPORTED_EXTENSIONS`、`AssetKind` 或任何代码常量中。** 三条理由：

1. **穷举不可能。** 除上述四类，用户还有纪录片、综艺、Vlog、短片、播客、访谈、网课、素材包……列不全的枚举就是坏枚举——用户永远发现自己的那一类不在选项里，只能被迫选一个不准确的。
2. **改一次要动代码。** 新增题材意味着改源码、重新构建、重新部署。而题材是用户每天都会长出来的东西，不该有这种代价。
3. **它已经有更好的实现。** 标签系统（`tags` / `asset_tags`）本就提供了：用户自建、可增删、参与检索、有使用计数、跨素材复用、`name_key` 判重。**题材就是标签的一种用法**，不需要第二套机制。

落地方式：

- 题材以标签形式住在数据库里，代码只认 `AssetKind`（video / audio / image / text）。
- **结构性保证**：`AssetKind = keyof typeof SUPPORTED_EXTENSIONS`。想新增一个题材键，就必须为它编出一组描述**文件类型**的扩展名——编不出来，就说明它本来就不属于这里。
- 界面上**不出现**「题材」筛选器；引导用户用标签表达题材（README 已给出「探店」「美食」的例子）。
- **备选：在 `SUPPORTED_EXTENSIONS` 旁并列一个 `GENRES` 常量用于筛选**——弃用，理由同上三条。

### 决策 12：提取按文件类型分派，字幕文件走零依赖的直接解析路径

「提取文字」不是一种操作，而是三种，成本差别极大：

| 文件类型 | 提取方式 | 依赖 |
|---|---|---|
| 音频 / 视频 | 语音转写 | `Xenova/whisper-small`，`dtype: 'q8'`，首次下载约 238 MB |
| 图片 / 视频画面 | OCR | `tesseract.js` + `chi_sim` 语言包 |
| **字幕文件（`.srt` / `.vtt` / `.ass` / `.ssa`）** | **直接解析** | **无** |

字幕文件是「文字已经现成」的素材：内容本就是纯文本，只是包了一层时间轴与样式标记。**对它跑 OCR/ASR 是既慢又差的重复劳动**——识别结果不可能比原文件更准，还要多下载几十 MB 模型。因此 `.srt` / `.vtt` / `.ass` / `.ssa` 归入 `text` 类，提取时走直接解析：读文件 → 剥离样式与定位标记 → 按条目产出带时间轴的段落 → 写入 `asset_text_segments`。

`.ass` / `.ssa` 的解析要点（纯字符串处理，无外部依赖）：

- 只取 `[Events]` 段的 `Dialogue:` 行；`[V4+ Styles]` 等样式头整段忽略。
- `Dialogue:` 的字段以逗号分隔，**`Text` 是第 10 个字段**，因此必须按前 9 个逗号切分，不能用「全部逗号切分再取最后一段」——对白里本身就可能含逗号。前 9 个依次是 `Layer, Start, End, Style, Name, MarginL, MarginR, MarginV, Effect`。
- 剥掉 `{\...}` 覆盖标签（含 `\pos`、`\an`、`\fad` 等绘图与定位指令）与 `\N` / `\n` 换行标记，再折叠空白。
- `.ssa` 与 `.ass` 同族（ASS 是 SSA 的超集），同一解析器即可覆盖。

这条路径的两个重要性质：

- **零模型依赖**，因此它可以在第二批的识别引擎就绪之前独立交付——甚至可以先于第一批之外的任何下载存在。
- **与「支持动漫素材」是同一件事的两面**：动漫与剧集素材的一大组成部分就是外挂字幕文件（`.ass` 在字幕组生态里几乎是默认格式）。让这批文件的正文可被检索，是「支持动漫素材」最直接、成本最低的一步。

**多语言的边界要说清楚**：字幕文件里现成的日文、英文文本**照常解析入库**——直接解析不「识别」任何东西，只是把文件里已有的字读出来，因此一份日文字幕的 `.ass` 完全可用。受限的只是**从语音和画面里认出日文/英文**，那需要另选模型与语言包。本变更的 ASR 与 OCR 只做中文。

### 决策 13：字形（简 / 繁）是提取链路的输入，且必须参与缓存键

**问题**：提取出的原文大量是繁体——Whisper 的中文输出默认就是繁体（实测一段普通话语音转写出「今天我們來探店這家火鍋店」），网上下载的外挂字幕繁体比例也很高。而检索是按字符匹配的，库里存繁体、用户搜简体就是零结果，**且不报任何错**。

**做法**：把字形做成用户偏好（设置页「默认文本保存方式」，存 `app_settings`），在提取落库前统一转换。用 `opencc-js` 做**字符级**转换（`cn` ↔ `tw`），刻意不用带词汇映射的 `twp`——说话人说的就是「開啟」，只该换字形，不该替他改词。

三处非显然的取舍：

1. **转换位置在落库前，不在读取时。** FTS 索引由触发器跟着 `asset_text_segments` 的行同步，索引里存的就是写入时的字。若只在读取时转换，库和索引仍是繁体，搜索照样零结果。**转换必须发生在触发器看到之前。**
2. **字形必须进 `extraction_runs.engine_versions`。** 落库文本随偏好而变，所以「同一文件 + 同一解析器版本」并不保证产出同一份文本。若缓存键不含字形，用户改完偏好再点提取会命中旧缓存拿到旧字形——**设置改了却毫无反应**，且全程无报错。实现为 `engineLabel(script) = \`${PARSER_VERSION}+${script}\``。
3. **试过、并且没用的办法：`initial_prompt` 偏置。** 实测给 Whisper 传「以下是普通话的句子，请使用简体中文转写」，输出与不传时**逐字相同**，全是繁体。所以后处理转换不是偷懒，是这代模型上唯一可行的路。

**Why**: 这条决策的价值不在「多了一个下拉框」，而在于它揭示了一类容易漏掉的耦合——**产物依赖于某个配置时，那个配置就必须是缓存键的一部分**。同类风险在「换个模型再提取」时同样成立。

## Risks / Trade-offs

- **[中文 OCR 精度不足]** → 优先用于字幕/画面文字等规整场景；允许手工修正提取文本；若实测不可接受，再引入 PaddleOCR 侧车（届时作为独立变更）。
- **[首次使用需下载 OCR 语言包与语音模型]** → 在首次启动引导中显式说明体积与耗时并展示进度；下载失败时降级为「仅元数据 + 文件名检索」，不阻断应用启动。
- **[本地明文存储 API Key]** → 目录不进版本库、文件权限收紧、界面与日志脱敏、README 警示。不追求系统级密钥链是本期的明确取舍。
- **[Whisper 在 CPU 上转写长视频极慢]** → 队列串行 + 任务可中断 + 指纹缓存避免重复；界面对长素材给出耗时预期提示。
- **[云端 API 按量计费]** → 发起前展示待处理文本量级，允许取消；失败不自动重试以免重复计费。
- **[服务可读取本机文件]** → 仅监听 `127.0.0.1` + Origin 校验；只访问用户显式配置的目录，不越界扫描。
- **[FTS5 中文检索召回不佳]** → **已实测并定案**：trigram 分词器 + 短词（≤2 字）LIKE 兜底，兜底范围含正文（实测 20 万段全表扫 24 ms）。逐词分流而非整串判断，避免「一个短词废掉整个查询」。详见决策 3。
- **[trigram 索引体积约为原文 4 倍]** → 采用 external content 表（把总占用从 6.8x 降到 5.4x）；索引写入搭提取任务的顺风车；README 给出容量预期。查询极快（5 万段 MATCH 仅 0.2 ms），这是正确的时空交换。
- **[题材无法在代码里精确分类]** → 不试图分类：题材由标签承载，代码只认文件类型（决策 11）。代价是刚导入的素材没有被自动标注题材，需要用户自己打标签；收益是任何新题材都不必改代码，且分类口径始终由用户掌握。
- **[日文/英文素材的语音与画面文字搜不到]** → 明确列入未来规划。缓解手段是字幕文件的直接解析（决策 12）：动漫与剧集素材的主要文字来源恰恰是外挂字幕，这部分照常可搜，受限的只是「从语音和画面里认出日文/英文」。
- **[字幕文件解析出错或格式变体多]** → 解析限 `.srt` / `.vtt` / `.ass` / `.ssa` 四种，只取对白与时间轴，不试图还原样式；解析不出字幕条目时按「已提取、文本为空」处理并给出提示，与既有的空结果语义一致。

## Migration Plan

全新项目，无数据迁移。首次部署流程为：

1. `npm install` 安装依赖。
2. 启动本地服务，浏览器自动/手动打开界面。
3. 首次启动引导：选择 OCR 与转写模型规格 → 下载模型 → 提示前往设置页填写 API Key（可跳过）。
4. 在素材库页添加素材目录 → 触发扫描 → 按需执行文字提取。

回滚策略：应用为纯本地运行，回滚即切换到上一版本代码；数据目录中的 SQLite 索引与提取结果在无破坏性迁移的前提下可直接复用，若索引结构变更则清空索引并重新扫描（原始素材文件不受影响）。

## 交付批次与未来规划

**第一批（已交付）**：设置 + 素材库 + 检索。验收标准：输入关键词能检索到本地素材，凭证可配置且不落库，**全程不依赖任何大模型下载**。

**第二批（本变更范围内，尚未实现）**：

- 文字提取——音频/视频语音转写（Transformers.js）、图片与视频画面 OCR（tesseract.js）
- **字幕文件直接解析导入**（`.srt` / `.vtt` / `.ass` / `.ssa`）——零模型依赖，见决策 12
- 文案润色与归档为标签

**未来规划（明确不在本变更范围内）**：

- **中文以外语言的语音转写与 OCR。** 日文、英文等语言需要另选 Whisper 模型与 tesseract 语言包，并重新验证准确率，工期上不纳入本变更。**字幕文件的直接解析不受此限**（见决策 12 末段）。
- **漫画压缩包（`.cbz` / `.cbr`）的解包与逐页识别。** 本期漫画素材以散图（`.jpg` / `.png` / `.webp`）形式支持；压缩包需要先解包、再按页序排列，属于独立的一块工作。
- 向量语义检索、跨设备同步、桌面客户端打包等增强项（见 Non-Goals）。
