# 关键词素材检索与文案润色工具

一个**完全在本机运行**的素材管理工具。输入关键词，就能在你自己的硬盘上找到相关的视频、音频、图片和文本素材，并（在后续版本中）把素材里的文字提取出来、润色成可直接使用的文案。

它不联网抓取任何内容，素材来源只有你自己指定的本地文件夹。

它面向的典型素材是**动漫、漫画、剧集、游戏**这类用于二次创作的东西：为混剪找一段台词、为解说找一格画面、为图文笔记找一句游戏原文。这些素材的形态差别很大——外挂字幕、散图、录屏、长视频——但需求是同一条：**用关键词，把散落在硬盘各处的那一段找出来**。

> **关于「题材」**：本工具支持的是**文件类型**（视频、音频、图片、文本/字幕），不是题材。动漫、漫画、剧、游戏这些题材**不在代码里分类**，而是由你**用标签自己表达**——原因见[为什么题材是标签，不是分类](#为什么题材是标签不是分类)。

## 它解决什么问题

做内容的人大多有这样的经历：明明记得半年前存过一段"深夜食堂探店"的视频，翻遍硬盘也找不到；找到了又要从头看一遍，把里面能用的句子抄下来；抄完还得再改一遍才像文案。

这套流程有三个可以自动化的环节，本工具各对应一块功能：

| 环节 | 现状 | 本工具的做法 |
|---|---|---|
| 找素材 | 靠回忆文件夹名，翻不动 | 关键词检索文件名、标签和**素材里的文字** |
| 抄文字 | 人工看、人工听 | 本地引擎自动转写与识别，零调用费用 |
| 改成文案 | 手工重写 | 云端大模型润色，密钥由你自己填 |

**核心取舍**：检索与文字提取全部在本机完成，不产生任何费用、不上传任何素材；只有"润色"这一步会把文字发给你自己配置的云端模型，且由你明确点击才会发生。

## 功能说明

### 当前已可用（第一批）

**素材库管理**

- 添加任意数量的本地文件夹作为素材目录，支持递归扫描子目录
- 识别视频、音频、图片、文本（含 `.srt` / `.vtt` / `.ass` / `.ssa` 字幕）四类共 30 余种扩展名；不支持的文件会被跳过，并**如实告诉你跳过了多少个**——这是"我明明有 500 个文件，怎么只索引了 80 个"唯一的解释来源
- 增量重扫：新增的文件建索引，修改过的更新，磁盘上已删除的记录清除，没变化的跳过
- 扫描在后台执行，界面实时显示进度，可随时取消
- **移除目录只清除索引，绝不删除磁盘上的原始文件**——这条由代码层面的 lint 规则强制保证，不是靠自觉

**关键词检索**

- 同时检索文件名、标签和已提取的正文，同一素材从多处命中时合并为一条结果
- 结果按可解释的档次排序（文件名/标签精确命中 → 部分命中 → 仅正文命中），而不是一个说不清含义的总分
- 展示命中上下文片段并高亮关键词，正文片段带时间轴标注
- 支持按素材类型、提取状态筛选，筛选条件可见、可一键清除

**标签**

- 给素材打标签，标签同样参与检索
- 自动判重：`MP4`、`mp4`、`ＭＰ４` 会被识别为同一个标签，前后空格也不影响
- **题材也用标签表达**：`动漫`、`番剧`、`漫画`、`游戏`、`混剪`……你想加什么就加什么，想怎么分类就怎么分类，不需要改代码。详见[下一节](#为什么题材是标签不是分类)

**凭证设置**

- 在界面上填写你自己的云端模型 API Key，无需改任何代码或配置文件
- 未配置时润色功能停用并给出提示，**检索与素材管理不受影响**

**文本保存方式（简体 / 繁体）**

- 设置页有一个「默认文本保存方式」下拉框，可选**简体中文（默认）**或**繁体中文**，改完立即保存
- 提取出的文字会先按这个选项统一字形，再存进素材库
- 为什么需要它：繁体和简体是**不同的字符**，检索又是按字符匹配的。库里存繁体、你搜简体，结果就是零，而且**不报任何错**。详见[检索能力的边界](#四繁简字形直接决定能不能搜到)

**文字提取**

- 在素材详情面板里点一下就能提取，进度实时显示，提取出的文字带时间轴展示在同一个面板里
- **字幕文件直接导入**：`.srt` / `.vtt` / `.ass` / `.ssa` 这几种文件里的文字**本来就已经是文字**，只是包了一层时间轴和样式标记。所以它们不走识别，直接解析导入——**不需要下载任何模型，也不限语言**（日文字幕照常导入、照常可搜），而且是瞬间完成
- **音频与视频的语音转写**：走本地 Whisper 模型（首次使用会下载约 241 MB，之后走缓存），依次完成「探测有没有音轨 → 导出 16 kHz 单声道音频 → 转写 → 按你设置的字形落库」，每段文字都带着在素材里的起止时间。**仅中文**。转写要跑几分钟到几十分钟，提交后进入队列**串行执行**（不会几个一起跑把 CPU 打满），可以离开这一页去做别的，回来进度还在
- 提取是**只读**的：它读你的文件、把文字写进索引，**绝不修改或删除原始素材**
- 提取结果会被检索命中，所以一段视频提取完，它里面说的每句话都变得可搜

**图片文字识别（OCR）暂不提供**——原因和实测数据见[未来规划](#图片文字识别ocr本地识别引擎)。在界面上，图片素材的提取按钮是禁用的，并会说明这一点，而不是让你点完再吃一个错误。

### 第二批（已规划，尚未实现）

> ⚠️ 下面这些功能**界面上都还没有入口**。把它们写在这里是为了让你知道项目要往哪走，而不是让你以为现在就能用。

- **文案润色**：把提取出的文字交给云端大模型润色成文案，支持多素材合并成一篇笔记
- **归档为标签**：把润色结果或提取的关键词直接归档成素材标签，下次检索即命中

### 未来规划（更远，当前不在计划内）

#### 图片文字识别（OCR，本地识别引擎）

**当前状态：不提供。** 图片素材（`.jpg` / `.png` / `.webp` 等）在界面上提取按钮是禁用的，会明确说明这一点。

这条不是「还没排上」，而是**评估之后主动挂起的**。评估时实际跑了一组合成图片的识别测试，数据如下：

| 测试场景 | 识别准确率 | 耗时 |
|---|---|---|
| 44px 清晰大字 | 90.5% | 63 ms |
| 20px 小字、灰底 | 100% | 29 ms |
| 28px **竖排**文字 | 83.3%（有丢字） | 14 ms |
| 22px、**网点纸背景**（原图直接识别） | **0.0%**（输出为空） | 66 ms |
| 同上，只做灰度化 + 放大 3 倍 | **8.3%**（乱码） | **31 秒** |
| 同上，**先二值化再放大 3 倍**（最近邻） | **100.0%** | 88 ms |

**几个结论值得写下来：**

1. **不需要下载模型。** 中文语言包随 npm 依赖一起落地（约 1.7 MB），worker 初始化 197 ms。所以「要不要下模型」不是问题。
2. **预处理是 0% 和 100% 之间的分水岭**，而且是**顺序敏感**的：必须「先二值化、再放大」，且放大要用最近邻。按常规思路走的「灰度化 → 放大」只到 8.3%，还慢了 350 倍（31 秒）。用错顺序不是效果差一点，是白干。
3. **上面这些数字是乐观上限。** 测试用的是合成图片（字体统一、无噪声、无边框）。真实的漫画与番剧截图会有手绘装饰字体、扫描噪声、对话气泡的边框与半透明底、简繁混排、拟声词——每一项都会把准确率往下拉，而**这些恰恰是本工具的目标素材**。
4. 成本上，把 OCR 接进现有链路（图像预处理、逐帧调度、结果与语音文本合并去重、失败降级）大约要 2～2.5 小时，是当时剩余工期的一半以上。

**取舍的理由**：识别质量的风险集中在最需要它的那类素材上，而工期是硬的。与其交付一个「对清晰截图好用、对真正的漫画基本不可用」的功能，不如先把字幕导入与语音转写做扎实——这两条路对动漫、剧集素材的覆盖率其实更高，而且不依赖识别质量。

**如果你现在就需要图片里的文字**：把图片的文件名写清楚（文件名参与检索，立刻生效），或者把它的台词/说明打成一个标签。另外，**画面里的硬字幕如果同时存在外挂字幕文件，导入字幕文件就能让这些文字可搜**——那条路不需要任何识别。

#### 其他

- **中文以外语言的语音转写与文字识别**（日文、英文等）。这需要另选模型和语言包并重新验证准确率，工期上排不进当前版本。
  **注意这条限制的边界**：它只针对「从语音和画面里认出文字」。**字幕文件的直接导入不受影响**——因为那只是把文件里已有的文本读出来，不涉及任何识别。所以一份日文外挂字幕完全可用；搜不到的只会是「视频里说的日文」和「画面上的日文」。
- **纯文本文件（`.txt` / `.md` / `.csv`）的导入**。它们本身已经是文字，障碍不是识别而是**编码判定**：中文纯文本大量是 GBK，判错了就是一整篇乱码进索引，比不导更糟。需要先做编码检测再谈导入。
- **漫画压缩包（`.cbz` / `.cbr`）**。现在漫画素材以散图（`.jpg` / `.png` / `.webp`）形式支持；压缩包需要先解包再按页序排列，是一块独立的工作。
- 向量语义检索（让「意思相近但字面不同」也能搜到）、跨设备同步、桌面客户端打包。

## 为什么题材是标签，不是分类

这一节回答一个很自然的问题：**为什么不能直接选「动漫 / 漫画 / 剧 / 游戏」？**

因为在代码里，**文件类型**和**题材**是两件完全不同的事：

| | 文件类型 | 题材 |
|---|---|---|
| 回答的问题 | **怎么读这个文件** | **内容讲什么** |
| 例子 | 视频、音频、图片、文本/字幕 | 动漫、漫画、剧、游戏、纪录片、综艺… |
| 谁说了算 | 文件本身 | **你自己** |
| 能不能穷举 | 能，就这四大类 | **不能** |

一个 `.mp4` 既可能是番剧、也可能是游戏录屏、还可能是你自己拍的 vlog。**同一个文件归到哪一类，取决于你怎么用它，而不取决于文件本身**——所以这件事代码猜不出来，也不该猜。

硬要把题材写进代码，会立刻带来三个麻烦：

1. **永远列不全。** 除了上面四类，你还有纪录片、综艺、Vlog、短片、播客、访谈、网课、素材包……写代码的人不可能替你想到所有分类。而一个列不全的分类，等于逼你在不准确的选项里挑一个。
2. **加一个题材要改代码。** 想加一类就得分支代码、重新构建、重新部署——而题材恰恰是你每天都会长出新东西的地方。
3. **它已经有了更好的家。** 标签系统本来就提供：自己建、随时删、参与检索、跨素材复用、自动判重。**题材就是标签的一种用法**，没必要再搞一套。

所以本工具的做法是：**代码只认文件类型，题材由你打标签。** 你在素材详情里打上「动漫」「番剧」这样的标签，它就立刻参与检索——想加多少加多少，代码一行都不用动。

这也是为什么 README 里反复说：**给素材打标签，是日后能找到它最可靠的方式。**

## 快速开始

```bash
# 1. 获取代码
git clone https://github.com/Kelsie-Ashton/material-search-and-text-polish.git
cd material-search-and-text-polish

# 2. 安装依赖（首次约需几分钟；会下载一个自带的 ffmpeg 二进制，属正常现象）
npm install

# 3. 同时启动后端与前端开发服务
npm run dev
```

启动后打开浏览器访问 **http://127.0.0.1:5173** 即可。

> 服务**只监听回环地址**（`127.0.0.1`），同一局域网内的其他设备无法访问。这是刻意的：本工具能读取你授权给它的任意本地目录，绝不应该暴露到网络上。

### 生产模式运行

如果不想每次开两个进程，可以先构建再由后端统一托管：

```bash
npm run build
npm start
```

然后访问 **http://127.0.0.1:5174**。

### 端口与数据目录

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `PORT` | `5174` | 后端监听端口 |
| `DATA_DIR` | `<项目根>/data` | 凭证、索引数据库、模型缓存的位置 |
| `HF_ENDPOINT` | `https://huggingface.co` | 语音模型的下载源。直连官方源太慢时改成 `https://hf-mirror.com`，只影响下载速度 |

需要修改时，把 `.env.example` 复制为 `.env` 后填写。**`.env` 已被 `.gitignore` 忽略，不会被提交。**

## 使用说明

### 第一步：配置凭证（可选）

打开 **设置** 页面，填入你的云端模型 API Key，点「保存」，再点「测试连通性」确认可用。

- 密钥只写进本机的 `data/credentials.json`，**不在任何源码或构建产物中**
- 页面上回显的只有末四位
- **不填也能用**：检索、素材库、标签全部正常，只有润色功能会保持停用状态

同一个页面上还有一项 **「默认文本保存方式」**（简体 / 繁体）。它不需要配置，默认就是简体；只有在你的素材本身以繁体为主、且你习惯用繁体搜索时，才需要改成繁体。改了会立即保存，不需要再点别处的按钮。详见[检索能力的边界](#四繁简字形直接决定能不能搜到)。

### 第二步：添加素材目录并扫描

1. 打开 **素材库** 页面
2. 在「素材目录」下填入一个本地文件夹的完整路径，例如 `D:\素材库`，可以顺便起个备注名
3. 点「添加目录」
4. 点该目录右侧的「扫描」
5. 看着进度条跑完，下方素材列表就会出现扫描到的文件

扫描结束后会给出这样一句总结：

> 扫描完成：发现 128 个文件，新增 96，更新 0，未变化 32，跳过 32 个不支持的文件。

**关于「跳过的不支持的文件」**：本工具只索引视频、音频、图片和文本。`.pdf`、`.psd`、`README`（无扩展名）这类文件会被跳过。这个数字不是错误，而是让你能对上账。

#### 增量重扫

再次点「扫描」是**增量**的：只有新增或修改过的文件会被处理，没变的不重复处理，磁盘上已经删掉的文件其记录也会被清除。所以素材有变动时，重新扫一次即可，代价很小。

#### 移除目录

点「移除」并确认后，该目录下的素材会从索引中消失。**磁盘上的文件和文件夹一个都不会被删除**，随时可以重新添加回来。

### 第三步：检索

在 **检索** 页面输入关键词，多个词用空格分开。

结果里每条素材会告诉你：

- **命中了哪些地方**：文件名 / 标签 / 正文
- **命中了哪些词**
- **正文里的上下文片段**，命中的词会高亮，带视频时间轴

### 第四步：给素材打标签

在素材库里点任意一条素材，详情面板会打开。在「标签」一栏输入名字回车即可，点标签上的 `×` 可以移除。

标签会参与检索，所以给素材打上「探店」「美食」这类短标签，是日后能找到它的最可靠方式——原因见下一节。

**题材也这样打**：`动漫`、`番剧`、`漫画`、`游戏`、`混剪`……这些不是系统给你的选项，而是你自己定的词汇。想怎么分类就怎么分类，随时可以加新的。

### 第五步：提取文字

**这一步决定了你的素材内容能不能被搜到。** 没提取过的视频，它里面说的每一句话都是搜不到的——只有文件名和标签能被搜到。

在素材库里点开任意一条素材，详情面板的「文字提取」一栏就是入口。按钮上的字会随素材类型变化：

| 素材类型 | 按钮 | 会发生什么 |
|---|---|---|
| 字幕文件 `.srt` `.vtt` `.ass` `.ssa` | 导入字幕文字 | **瞬间完成**，不下载任何模型 |
| 音频、视频 | 提取语音文字 | 提交到队列，跑本地转写，几分钟到几十分钟 |
| 图片 | 识别图片文字 | **禁用**，OCR 暂不提供（见[未来规划](#图片文字识别ocr本地识别引擎)） |
| 其他纯文本 `.txt` `.md` | — | 禁用，障碍是编码判定，见未来规划 |

几个实际使用上的提醒：

- **视频提取的是「声音」，不是「画面上的字」。** 如果你要的是画面里的硬字幕，而手头正好有配套的字幕文件，**导字幕文件比转写快得多也准得多**——转写还可能在背景音乐、多人抢话的地方出错。
- **转写是串行的，而且可以离开。** 一次提交多个素材，它们会一个接一个地跑，不会互相争抢 CPU。进度显示在素材列表对应那一行，也在详情面板里。转写中途刷新页面或关掉浏览器都不影响它，任务在后端继续跑。
- **提取完成后，文字立刻就能被检索命中**，带时间轴。点检索结果里的「定位」能看到它出现在素材的哪一分哪一秒。
- **提取是只读的**，不会修改或删除你的原始文件。
- 首次转写会下载约 241 MB 的语音模型，之后走本地缓存。模型下载失败或断网时，字幕导入仍然可用。
- **模型下不动就先换下载源。** 默认从 huggingface.co 拉，多数网络下它最快；但有些网络直连它极慢（本项目开发机实测 0.07 MB/s，241 MB 要将近一小时），这时在 `.env` 里加一行 `HF_ENDPOINT=https://hf-mirror.com` 重启即可，实测能到分钟级。换源只改下载地址，模型本身不变。

#### 哪些情况会「提取了但没文字」

这**不代表失败**，也不需要重试：

- 视频里没有人说话（纯画面、纯音乐、只有环境音）
- 音频是纯音乐或纯音效
- 字幕文件是空的，或格式不被识别

详情面板会就此给出说明，而不是留一个空列表让你猜。

## 检索能力的边界

这一节讲的是**为什么有些词搜不到**。知道这些，能省下大量"程序是不是坏了"的困惑。

### 一、正文检索依赖已提取的文字

只有**已经做过文字提取**的素材，它里面的语音和画面文字才进得了检索范围。

> **搜不到 ≠ 素材里没有。**
> 如果你还没对视频执行过文字提取，那么视频里说的每一句话都是搜不到的。这就是[第五步](#第五步提取文字)存在的全部理由——**提取过的素材才会进正文索引**。

**最省力的例外是字幕文件。** 如果你手头有配套的 `.ass` / `.srt` / `.vtt` 字幕（动漫和剧集素材通常都有），那么导入它就能让整段视频的台词变得可搜——**不需要下载任何模型，也不需要等语音转写跑完**，而且是瞬间完成。这条路径不受「仅中文」的限制。

**给视频起个好文件名，是当下最立竿见影的办法**：把「第几集」「哪一段」写进文件名，因为它现在就能被搜到。

### 二、不足 3 个字的词走的是另一条路

中文分词索引（trigram）无法处理少于 3 个字符的词。所以：

- **3 个字及以上**（如「火锅店」「深夜食堂」）→ 走正文分词索引，快且精确
- **2 个字及以下**（如「探店」「美食」「剪辑」）→ 改用全库扫描匹配

这两条路径的结果形态确实不同，所以当你用了短词时，界面会明确告诉你：

> 探店 不足 3 个字，已改用全库扫描匹配

这不是警告你出错了，只是让你知道这次搜索是怎么做的。**两字词能搜到结果**，只是代价是扫描范围更大。

### 三、多个关键词是「任一命中即召回」

搜「深夜 火锅店」时，只命中「深夜」的素材也会出现在结果里，只是排得靠后。

这样设计是因为素材里的文字来自语音转写和图片识别，本身就可能带错字。如果用「必须全部命中」，那么一个词写错，整次检索就归零了；现在则是命中的部分照样浮上来，由排序把命中词更多的排到前面。

### 四、繁简字形直接决定能不能搜到

**「火锅店」和「火鍋店」在程序眼里是两个完全不同的字符串。** 检索是按字符匹配的，不是按读音或含义，所以你在库里存繁体、用简体搜，结果就是**零**——而且不会有任何报错或提示，看起来就像那个素材从没提过这件事。

麻烦在于，**提取出来的原文常常是繁体**：

- 网上下载的外挂字幕，繁体版本占相当大比例
- 本地语音转写（Whisper）的中文输出**默认就是繁体**，实测一段普通话语音转写出的是「今天我們來探店這家火鍋店」

所以在**文字写入素材库之前**，本工具会按设置页的「默认文本保存方式」统一转换字形：选简体（默认）就转成简体，选繁体就转成繁体。

几点如实说明：

- **只换字形，不改用词。** 「開啟」转成「开启」，而不是改写成「打开」；「軟件」转成「软件」，而不是台湾用词「軟體」。转写场景下说话人说的是什么就该是什么，工具不该替他改词。
- **默认选简体**，因为简体检索是大多数人的预期。
- **改动只影响之后提取的文字。** 文本是在提取时就落库的，所以改完设置后，已经提取过的素材需要**重新提取一次**才会按新字形重新入库。好消息是不用担心白跑——重新提取时缓存会识别出字形变了，会真的重跑，而不是糊弄你一下。
- **怎么选**：以你**搜索时习惯打的字**为准。你平时打简体就选简体，打繁体就选繁体——顺带一提，你的搜索习惯和素材本身的字形无关，一份繁体字幕照样能被简体关键词搜到，因为入库时已经统一了。

另外这条限制只针对**字形**（简繁），与**语言**无关：日文字幕文件照常导入、照常可搜，它的文字不含简繁差异，转换不会碰它。

## 数据存放与容量预期

所有运行时数据都在项目根目录的 `data/` 下，**整个目录已被 `.gitignore` 忽略**：

```
data/
├── credentials.json    你的 API Key（明文，仅存本机）
├── index.db            SQLite 索引数据库
└── models/             后续版本的语言包与转写模型缓存
```

### 磁盘占用

索引数据库的大小主要由**已提取的正文文字量**决定：

| 已提取文本量 | 数据库文件约 |
|---|---|
| 10 MB | 55 MB |
| 50 MB | 270 MB |
| 100 MB | 540 MB |

这是因为中文子串检索需要建立字符三元组索引，净开销约为原文的 4 倍。这是 SQLite 中文全文检索的固有代价，换来的是查询极快（5 万段文本的匹配查询约 0.2 毫秒）。

**如果暂时不做文字提取**，数据库会非常小——只有文件名、路径和标签，几万条素材也不过几 MB。

想回收空间，最直接的办法是在素材库里移除不再需要的目录：索引随之清除，磁盘上的原始文件不受影响。

## 关于 API Key 的安全说明

**这个项目的代码里没有任何 API Key，一个都没有。**

### 为什么

密钥写死在代码里，一旦提交到 GitHub 就等于公开泄露——爬虫扫到它只需要几分钟。而且这类泄露无法撤回：即使你发现后删除，密钥也已经在别人的数据库里了。

所以本项目从架构上就不给这件事发生的可能：

1. **密钥只能由你在界面上填写**，保存在本机的 `data/credentials.json`
2. **密钥不从环境变量读取**。这是刻意的：让"密钥在哪里"只有一个答案。如果同时支持环境变量，就可能出现"界面显示未配置、实际却在用某个旧 Key"，并让"清空凭证即停用润色"变得不可靠
3. `data/` 整个目录被 `.gitignore` 忽略
4. 仓库里有一个自动检查脚本（`npm run check:secrets`），在提交前扫描全部源码与文档，发现疑似密钥特征串就报错

### 提交前请自行确认

```bash
npm run check:secrets   # 扫描疑似密钥
git status              # 确认列表里没有 data/ 与任何凭证文件
```

### 如实说明一处局限

`data/credentials.json` 在创建时会尝试设置为仅本人可读（POSIX 权限 `600`）。但**在 Windows 上这个权限位基本不起作用**——真实的保护来自文件所在用户目录的访问控制，以及这个目录不会被提交到任何仓库。

也就是说：**同机器上的其他用户账户有可能读到这个文件**。如果你的电脑是多人共用的，请自行评估；这不是本工具能在应用层解决的问题。

### 一些实现上的约定

- **可预期的业务失败一律通过 `Result` 返回，不抛异常。** 只有"不该发生"的编程错误才 `throw`。错误码到 HTTP 状态码的映射只在一处（`shared/http.ts`）。
- **路由层只做参数校验与结果写回**，业务逻辑在各自的 service 模块里，可以直接被单测调用，不必起 HTTP 服务。
- **`library/` 目录下禁止调用任何文件删除 API**，由 ESLint 规则强制。这条规则的存在让"移除目录只清索引"从一个口头承诺变成编译期约束。
- **代码里只有文件类型，没有题材。** `AssetKind` 由 `SUPPORTED_EXTENSIONS` 的四个键推导（video / audio / image / text），想往里加一个题材键就必须为它编出一组扩展名——编不出来就说明它不属于那里。题材一律走标签。详见[为什么题材是标签，不是分类](#为什么题材是标签不是分类)。

## 技术选型

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言 | TypeScript（前后端统一） | 类型安全，接口契约可复用 |
| 后端 | Node.js + Express 5 | 轻量成熟，生态稳定 |
| 前端 | React + Vite | 构建快，开发体验好 |
| 存储 | SQLite（better-sqlite3）+ FTS5 | 单文件零运维；**必须用 better-sqlite3 而非 Node 内置的 `node:sqlite`——后者未编译 FTS5** |
| 检索 | FTS5 trigram 分词器 + 短词 LIKE 兜底 | 对中文子串检索容忍度高；两字词由兜底路径覆盖 |
| 语音转写 | Transformers.js（`@huggingface/transformers`，纯 WASM） | 零编译，Windows 上装得稳；`return_timestamps` 直接给时间轴 |
| 抽帧/抽音轨 | `ffmpeg-static` | 自带 ffmpeg 二进制，用户无需自行安装 |
| 繁简转换 | opencc-js | 纯 JS、无原生依赖；用字符级转换（`cn`/`tw`）而非词汇级（`twp`），只换字形不改用词 |
| 测试 | Vitest | 前后端共用一套 |

**明确不引入**：Redis、消息队列、独立数据库服务、Python 运行时、原生编译工具链、向量数据库。这是个单用户的本机应用，引入这些只会增加安装失败的几率。

**OCR（tesseract.js）不在上表里**：依赖装了、评估也做完了，但功能被主动挂起，理由与实测数据见[未来规划](#图片文字识别ocr本地识别引擎)。所以 `package.json` 里会有这个依赖，而界面上没有它的入口——这不是漏了，是刻意留着的。

技术选型的实测过程记录在 `spikes/` 与 `openspec/` 下——包括为什么放弃 jieba 分词、为什么文件名和标签不进分词索引、trigram 索引到底占多少磁盘。这些结论都是跑出来的，不是查出来的。

## 常见问题

**问：扫描很慢，正常吗？**

取决于文件数量和磁盘速度。扫描只读取文件的元信息（大小、修改时间），不读文件内容，所以通常很快——几万个文件的目录一般在几十秒内完成。第一次扫描最慢，之后是增量的。

**问：为什么索引里的文件数比我文件夹里的少？**

因为只有视频、音频、图片和文本（含字幕）会被索引。扫描结束后会明确告诉你跳过了多少个不支持的文件。如果数量对不上，检查一下是不是有一批 `.pdf`、工程文件或压缩包（`.zip` / `.cbz` / `.cbr` 里的内容不会被展开，压缩包本身也不索引）。

**问：我是做动漫 / 漫画 / 剧集 / 游戏素材的，这东西适合我吗？**

适合，而且这几类正是它主要面向的素材。它们共同的特点是：素材散、量大、形态杂（外挂字幕、散图、录屏、长视频），而你要找的往往只是其中一小段。

对这几类素材，**最值得先做的一件事是导入字幕文件**：番剧和剧集通常都带外挂字幕（`.ass` / `.srt`），导入是瞬间完成的，导完整个视频的台词就都能搜了。其次是语音转写（转的是声音，画面上的字要等 OCR）。再退一步，**给素材打好题材标签、把关键信息写进文件名**，这些立刻生效。

**问：能按「动漫」「游戏」这样的题材筛选吗？**

不能，而且这是刻意的设计——**题材不在代码里分类，而是由你用标签表达**。所以正确做法是给素材打上「动漫」「游戏」这样的标签，然后用检索找它们（标签是参与检索的）。为什么这么设计，见[为什么题材是标签，不是分类](#为什么题材是标签不是分类)。

**问：日文 / 英文的素材能用吗？**

分两种情况，差别很重要：

- **字幕文件（`.ass` / `.srt` / `.vtt` / `.ssa`）——可以，不限语言。** 因为字幕文件里的文字本来就是现成的，程序只是把它读出来，不需要「认出」它是什么语言。所以一份日文外挂字幕完全可用：在素材详情面板点「导入字幕文字」即可。
- **视频里的日文语音、画面上的日文——暂时不行。** 语音转写和 OCR 当前只配置了中文，多语言识别列在「未来规划」里，当前版本不实现。

**问：能不能扫描网络位置或移动硬盘？**

只要是本机可访问的路径都可以添加。但移动硬盘拔掉后重新插上（盘符变化）会导致路径失效，需要重新添加。

**问：搜不到明明存在的素材？**

先看[检索能力的边界](#检索能力的边界)。最常见的原因有三个：搜的是不足 3 个字的词（会走全库扫描，仍能搜到但要慢一些）；搜的内容在视频语音/图片里而该素材还没做过文字提取；以及**繁简不匹配**——库里存的是繁体而你搜的是简体（或反过来），两边字符对不上，就是零结果。最后这一条现在由设置页的「默认文本保存方式」统一处理，默认存简体。

**问：我改了「默认文本保存方式」，为什么旧素材还是搜不到？**

因为文本是**提取时就落库**的，改设置不会回头重写已经入库的内容——设置只对之后提取的文字生效。要让某个素材按新字形重新入库，得对它**重新提取一次**。重新提取时缓存会识别出字形变了，会真的重跑，不会因为"文件没变"就跳过。

（提取功能的界面入口属于第二批，见[功能说明](#功能说明)。在入口可用之前，这个设置项本身可以正常修改和保存，只是还没有可提取的对象。）

**问：这个工具会把我的文件传到网上吗？**

不会。扫描、检索、标签全部在本机完成。唯一会联网的操作是**你明确点击的润色**，它把文字（不是文件）发送到你自己配置的模型服务。搜索引擎与素材库不联网，不抓取任何网络内容。

**问：不填 API Key 能用吗？**

能。检索、素材库、标签、以及后续的文字提取功能都不依赖它，只有润色需要。未配置时润色入口会显示为停用并说明原因。
