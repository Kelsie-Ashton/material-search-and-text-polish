# 关键词素材检索与文案润色工具

一个**完全在本机运行**的素材管理工具。输入关键词，就能在你自己的硬盘上找到相关的视频、音频、图片和文本素材，并（在后续版本中）把素材里的文字提取出来、润色成可直接使用的文案。

它不联网抓取任何内容，素材来源只有你自己指定的本地文件夹。

## 它解决什么问题

做内容的人大多有这样的经历：明明记得半年前存过一段"深夜食堂探店"的视频，翻遍硬盘也找不到；找到了又要从头看一遍，把里面能用的句子抄下来；抄完还得再改一遍才像文案。

这套流程有三个可以自动化的环节，本工具各对应一块功能：

| 环节 | 现状 | 本工具的做法 |
|---|---|---|
| 找素材 | 靠回忆文件夹名，翻不动 | 关键词检索文件名、标签和**素材里的文字** |
| 抄文字 | 人工看、人工听 | 本地引擎自动转写与识别，零调用费用 |
| 改成文案 | 手工重写 | 云端大模型润色，密钥由你自己填 |

**核心取舍**：检索与文字提取全部在本机完成，不产生任何费用、不上传任何素材；只有"润色"这一步会把文字发给你自己配置的云端模型，且由你明确点击才会发生。

## 功能说明

### 当前已可用（第一批）

**素材库管理**

- 添加任意数量的本地文件夹作为素材目录，支持递归扫描子目录
- 识别视频、音频、图片、文本四类共 30 余种扩展名；不支持的文件会被跳过，并**如实告诉你跳过了多少个**——这是"我明明有 500 个文件，怎么只索引了 80 个"唯一的解释来源
- 增量重扫：新增的文件建索引，修改过的更新，磁盘上已删除的记录清除，没变化的跳过
- 扫描在后台执行，界面实时显示进度，可随时取消
- **移除目录只清除索引，绝不删除磁盘上的原始文件**——这条由代码层面的 lint 规则强制保证，不是靠自觉

**关键词检索**

- 同时检索文件名、标签和已提取的正文，同一素材从多处命中时合并为一条结果
- 结果按可解释的档次排序（文件名/标签精确命中 → 部分命中 → 仅正文命中），而不是一个说不清含义的总分
- 展示命中上下文片段并高亮关键词，正文片段带时间轴标注
- 支持按素材类型、提取状态筛选，筛选条件可见、可一键清除

**标签**

- 给素材打标签，标签同样参与检索
- 自动判重：`MP4`、`mp4`、`ＭＰ４` 会被识别为同一个标签，前后空格也不影响

**凭证设置**

- 在界面上填写你自己的云端模型 API Key，无需改任何代码或配置文件
- 未配置时润色功能停用并给出提示，**检索与素材管理不受影响**

### 规划中（第二批，尚未实现）

> ⚠️ 下面这些功能**当前代码里还没有**。把它们写在这里是为了让你知道项目要往哪走，而不是让你以为现在就能用。克隆下来跑起来后，界面上与提取、润色相关的入口会明确显示为未开放。

- **文字提取**：视频与音频的语音转写（本地 Whisper 模型，带时间轴），图片与视频画面的文字识别（本地 tesseract.js，中文）
- **文案润色**：把提取出的文字交给云端大模型润色成文案，支持多素材合并成一篇笔记
- **归档为标签**：把润色结果或提取的关键词直接归档成素材标签，下次检索即命中

## 快速开始

```bash
# 1. 获取代码
git clone <仓库地址>
cd my-vibe-project

# 2. 安装依赖（首次约需几分钟；会下载一个自带的 ffmpeg 二进制，属正常现象）
npm install

# 3. 同时启动后端与前端开发服务
npm run dev
```

启动后打开浏览器访问 **http://127.0.0.1:5173** 即可。

> 服务**只监听回环地址**（`127.0.0.1`），同一局域网内的其他设备无法访问。这是刻意的：本工具能读取你授权给它的任意本地目录，绝不应该暴露到网络上。

### 生产模式运行

如果不想每次开两个进程，可以先构建再由后端统一托管：

```bash
npm run build
npm start
```

然后访问 **http://127.0.0.1:5174**。

### 端口与数据目录

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `PORT` | `5174` | 后端监听端口 |
| `DATA_DIR` | `<项目根>/data` | 凭证、索引数据库、模型缓存的位置 |

需要修改时，把 `.env.example` 复制为 `.env` 后填写。**`.env` 已被 `.gitignore` 忽略，不会被提交。**

## 使用说明

### 第一步：配置凭证（可选）

打开 **设置** 页面，填入你的云端模型 API Key，点「保存」，再点「测试连通性」确认可用。

- 密钥只写进本机的 `data/credentials.json`，**不在任何源码或构建产物中**
- 页面上回显的只有末四位
- **不填也能用**：检索、素材库、标签全部正常，只有润色功能会保持停用状态

### 第二步：添加素材目录并扫描

1. 打开 **素材库** 页面
2. 在「素材目录」下填入一个本地文件夹的完整路径，例如 `D:\素材库`，可以顺便起个备注名
3. 点「添加目录」
4. 点该目录右侧的「扫描」
5. 看着进度条跑完，下方素材列表就会出现扫描到的文件

扫描结束后会给出这样一句总结：

> 扫描完成：发现 128 个文件，新增 96，更新 0，未变化 32，跳过 32 个不支持的文件。

**关于「跳过的不支持的文件」**：本工具只索引视频、音频、图片和文本。`.pdf`、`.psd`、`README`（无扩展名）这类文件会被跳过。这个数字不是错误，而是让你能对上账。

#### 增量重扫

再次点「扫描」是**增量**的：只有新增或修改过的文件会被处理，没变的不重复处理，磁盘上已经删掉的文件其记录也会被清除。所以素材有变动时，重新扫一次即可，代价很小。

#### 移除目录

点「移除」并确认后，该目录下的素材会从索引中消失。**磁盘上的文件和文件夹一个都不会被删除**，随时可以重新添加回来。

### 第三步：检索

在 **检索** 页面输入关键词，多个词用空格分开。

结果里每条素材会告诉你：

- **命中了哪些地方**：文件名 / 标签 / 正文
- **命中了哪些词**
- **正文里的上下文片段**，命中的词会高亮，带视频时间轴

### 第四步：给素材打标签

在素材库里点任意一条素材，详情面板会打开。在「标签」一栏输入名字回车即可，点标签上的 `×` 可以移除。

标签会参与检索，所以给素材打上「探店」「美食」这类短标签，是日后能找到它的最可靠方式——原因见下一节。

## 检索能力的边界

这一节讲的是**为什么有些词搜不到**。知道这些，能省下大量"程序是不是坏了"的困惑。

### 一、正文检索依赖已提取的文字

只有**已经做过文字提取**的素材，它里面的语音和画面文字才进得了检索范围。

> **搜不到 ≠ 素材里没有。**
> 如果你还没对视频执行过文字提取，那么视频里说的每一句话都是搜不到的。这在当前版本尤其要注意——文字提取功能在第二批才会提供，所以在第一批里，**检索实际覆盖的是文件名和标签**。

### 二、不足 3 个字的词走的是另一条路

中文分词索引（trigram）无法处理少于 3 个字符的词。所以：

- **3 个字及以上**（如「火锅店」「深夜食堂」）→ 走正文分词索引，快且精确
- **2 个字及以下**（如「探店」「美食」「剪辑」）→ 改用全库扫描匹配

这两条路径的结果形态确实不同，所以当你用了短词时，界面会明确告诉你：

> 探店 不足 3 个字，已改用全库扫描匹配

这不是警告你出错了，只是让你知道这次搜索是怎么做的。**两字词能搜到结果**，只是代价是扫描范围更大。

### 三、多个关键词是「任一命中即召回」

搜「深夜 火锅店」时，只命中「深夜」的素材也会出现在结果里，只是排得靠后。

这样设计是因为素材里的文字来自语音转写和图片识别，本身就可能带错字。如果用「必须全部命中」，那么一个词写错，整次检索就归零了；现在则是命中的部分照样浮上来，由排序把命中词更多的排到前面。

## 数据存放与容量预期

所有运行时数据都在项目根目录的 `data/` 下，**整个目录已被 `.gitignore` 忽略**：

```
data/
├── credentials.json    你的 API Key（明文，仅存本机）
├── index.db            SQLite 索引数据库
└── models/             后续版本的语言包与转写模型缓存
```

### 磁盘占用

索引数据库的大小主要由**已提取的正文文字量**决定：

| 已提取文本量 | 数据库文件约 |
|---|---|
| 10 MB | 55 MB |
| 50 MB | 270 MB |
| 100 MB | 540 MB |

这是因为中文子串检索需要建立字符三元组索引，净开销约为原文的 4 倍。这是 SQLite 中文全文检索的固有代价，换来的是查询极快（5 万段文本的匹配查询约 0.2 毫秒）。

**如果暂时不做文字提取**，数据库会非常小——只有文件名、路径和标签，几万条素材也不过几 MB。

想回收空间，最直接的办法是在素材库里移除不再需要的目录：索引随之清除，磁盘上的原始文件不受影响。

## 关于 API Key 的安全说明

**这个项目的代码里没有任何 API Key，一个都没有。**

### 为什么

密钥写死在代码里，一旦提交到 GitHub 就等于公开泄露——爬虫扫到它只需要几分钟。而且这类泄露无法撤回：即使你发现后删除，密钥也已经在别人的数据库里了。

所以本项目从架构上就不给这件事发生的可能：

1. **密钥只能由你在界面上填写**，保存在本机的 `data/credentials.json`
2. **密钥不从环境变量读取**。这是刻意的：让"密钥在哪里"只有一个答案。如果同时支持环境变量，就可能出现"界面显示未配置、实际却在用某个旧 Key"，并让"清空凭证即停用润色"变得不可靠
3. `data/` 整个目录被 `.gitignore` 忽略
4. 仓库里有一个自动检查脚本（`npm run check:secrets`），在提交前扫描全部源码与文档，发现疑似密钥特征串就报错

### 提交前请自行确认

```bash
npm run check:secrets   # 扫描疑似密钥
git status              # 确认列表里没有 data/ 与任何凭证文件
```

### 如实说明一处局限

`data/credentials.json` 在创建时会尝试设置为仅本人可读（POSIX 权限 `600`）。但**在 Windows 上这个权限位基本不起作用**——真实的保护来自文件所在用户目录的访问控制，以及这个目录不会被提交到任何仓库。

也就是说：**同机器上的其他用户账户有可能读到这个文件**。如果你的电脑是多人共用的，请自行评估；这不是本工具能在应用层解决的问题。

```
│       ├── search/         检索：归一、召回、排序、上下文片段
│       └── routes/         HTTP 路由（只做参数校验与结果写回）

│       ├── components/     可复用组件
│       └── pages/          检索 / 素材库 / 设置
├── openspec/               规范驱动开发的规划文档
├── scripts/                密钥扫描等工具脚本
├── spikes/                 技术选型的实验脚本与实测数据
└── data/                   运行时数据（不提交）
```

### 一些实现上的约定

- **可预期的业务失败一律通过 `Result` 返回，不抛异常。** 只有"不该发生"的编程错误才 `throw`。错误码到 HTTP 状态码的映射只在一处（`shared/http.ts`）。
- **路由层只做参数校验与结果写回**，业务逻辑在各自的 service 模块里，可以直接被单测调用，不必起 HTTP 服务。
- **`library/` 目录下禁止调用任何文件删除 API**，由 ESLint 规则强制。这条规则的存在让"移除目录只清索引"从一个口头承诺变成编译期约束。

## 技术选型

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言 | TypeScript（前后端统一） | 类型安全，接口契约可复用 |
| 后端 | Node.js + Express 5 | 轻量成熟，生态稳定 |
| 前端 | React + Vite | 构建快，开发体验好 |
| 存储 | SQLite（better-sqlite3）+ FTS5 | 单文件零运维；**必须用 better-sqlite3 而非 Node 内置的 `node:sqlite`——后者未编译 FTS5** |
| 检索 | FTS5 trigram 分词器 + 短词 LIKE 兜底 | 对中文子串检索容忍度高；两字词由兜底路径覆盖 |
| 测试 | Vitest | 前后端共用一套 |

**明确不引入**：Redis、消息队列、独立数据库服务、Python 运行时、原生编译工具链、向量数据库。这是个单用户的本机应用，引入这些只会增加安装失败的几率。

技术选型的实测过程记录在 `spikes/` 与 `openspec/` 下——包括为什么放弃 jieba 分词、为什么文件名和标签不进分词索引、trigram 索引到底占多少磁盘。这些结论都是跑出来的，不是查出来的。

## 常见问题

**问：扫描很慢，正常吗？**

取决于文件数量和磁盘速度。扫描只读取文件的元信息（大小、修改时间），不读文件内容，所以通常很快——几万个文件的目录一般在几十秒内完成。第一次扫描最慢，之后是增量的。

**问：为什么索引里的文件数比我文件夹里的少？**

因为只有视频、音频、图片和文本会被索引。扫描结束后会明确告诉你跳过了多少个不支持的文件。如果数量对不上，检查一下是不是有一批 `.pdf` 或工程文件。

**问：能不能扫描网络位置或移动硬盘？**

只要是本机可访问的路径都可以添加。但移动硬盘拔掉后重新插上（盘符变化）会导致路径失效，需要重新添加。

**问：搜不到明明存在的素材？**

先看[检索能力的边界](#检索能力的边界)。最常见的原因有两个：搜的是不足 3 个字的词（会走全库扫描，仍能搜到但要慢一些），或者搜的内容在视频语音/图片里而该素材还没做过文字提取。

**问：这个工具会把我的文件传到网上吗？**

不会。扫描、检索、标签全部在本机完成。唯一会联网的操作是**你明确点击的润色**，它把文字（不是文件）发送到你自己配置的模型服务。搜索引擎与素材库不联网，不抓取任何网络内容。

**问：不填 API Key 能用吗？**

能。检索、素材库、标签、以及后续的文字提取功能都不依赖它，只有润色需要。未配置时润色入口会显示为停用并说明原因。
